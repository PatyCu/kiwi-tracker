# Kiwi Tracker

A mobile-first pet care and health tracker for iOS and web.

> Status: prototype

## Prerequisites

- Node.js 22
- npm 10
- Xcode and an iOS Simulator for iOS development

## Install

```bash
npm ci
```

## Develop

```bash
npm start
```

From the Expo terminal, press `w` to open the web app or `i` to open the iOS Simulator.

## Backend (Supabase)

The app currently stores data on the device. It is moving to [Supabase](https://supabase.com), where pets, events and photos are shared within a household. The database schema is ready; the app does not connect to it yet, so you only need this setup to work on the database.

### Get a Supabase project

- **Shared project:** ask the maintainer to invite you to the Supabase organization that owns the `kiwi-tracker` project.
- **Your own project, for development:** create a free project at [supabase.com/dashboard](https://supabase.com/dashboard), preferably in an EU region like the shared one. Then, in **SQL Editor**, run each file in `supabase/migrations/` in filename order.

Check the setup in the dashboard: **Table Editor** lists `households`, `household_members`, `pets` and `pet_events`, and **Storage** has a private `pet-photos` bucket.

### Give someone access to a household

Users are managed by Supabase Auth and appear under **Authentication → Users**, not in the Table Editor. A user only sees a household's data once they are a member of it.

1. In **Authentication → Users**, invite the person by email.
2. In **SQL Editor**, create a household if needed and add the user to it:

   ```sql
   insert into public.households (name) values ('Our pets') returning id;

   insert into public.household_members (user_id, household_id, display_name)
   values ('<user id from Authentication → Users>', '<household id>', '<name>');
   ```

Each user can belong to one household. The app cannot create households or change members; this is done only from the dashboard.

### Change the schema

- Add a new file to `supabase/migrations/` named `<YYYYMMDDHHMMSS>_<description>.sql`. Never edit a migration that has already been applied.
- Every table follows the same conventions: a `uuid` `id` generated by the database, and `created_at` and `updated_at` columns kept up to date by triggers. The app never writes these columns.
- Every table has row-level security enabled, with access limited to members of the row's household.
- After applying a migration, check **Advisors → Security Advisor** in the dashboard for new warnings.
